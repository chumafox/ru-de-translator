# План глубокой оптимизации RU-DE Translator для Apple Silicon (M1 Air 8GB)

Проект имеет отличную модульную архитектуру, поддерживает современные подходы (TUI на Textual, локальные LLM, MLX). Однако, для стабильной и комфортной работы на MacBook Air M1 с 8 ГБ объединенной памяти, есть несколько критических архитектурных "узких мест", приводящих к лишнему расходу RAM и потере real-time отзывчивости.

Ниже представлен подробный план оптимизации, который позволит сделать приложение молниеносным и "легким", не ухудшая качество перевода и синтеза речи.

---

## 1. Решение проблемы задержки TTS (Полноценный Streaming)
**Текущая проблема:** 
В `tts.py` генерация аудио (Qwen3-TTS) работает в потоковом режиме, выдавая `f32le` чанки. Однако поток `_player_thread` пишет их в `ffmpeg` для конвертации в файл `/tmp/rude_last.m4a`, затем ждет завершения конвертации (`proc.wait()`), и **только потом** запускает воспроизведение через `afplay`. Это полностью убивает смысл стриминга — пользователь ждет окончания генерации всей фразы перед тем, как услышит первый звук.

**Решение:**
- **Вариант А (Лучший для отзывчивости):** Использовать библиотеку `sounddevice` (или `pyaudio`) для прямого воспроизведения NumPy массивов (`f32le`) прямо из памяти по мере их генерации моделью MLX. Это даст нулевую задержку.
- **Вариант Б (Без новых зависимостей):** Перенаправить pipe напрямую в `ffplay`: 
  `ffplay -f f32le -ar 24000 -ac 1 -nodisp -autoexit -i pipe:0`.
  Это позволит `ffplay` воспроизводить чанки немедленно по мере их поступления в pipe.
- **Исправление кэширования:** Сейчас при попадании фразы в кэш (`_play_chunks`), скрипт заново прогоняет сохраненные сырые чанки через `ffmpeg` в `m4a` и затем играет. Необходимо кэшировать либо сразу в файл на диск, либо (при прямом воспроизведении через `sounddevice`) просто отправлять готовый массив в аудио-буфер без перекодирования.

## 2. Экстремальное похудение зависимостей (Удаление PyTorch)
**Текущая проблема:**
В `pyproject.toml` жестко прописаны `torch>=2.12.0`, `torchaudio>=2.1.0` и `accelerate`. PyTorch — это гигантский фреймворк, загрузка которого потребляет значительное количество оперативной памяти (что критично для 8GB) и места на диске (~1-2 ГБ). 

**Решение:**
- **Для CTranslate2:** Эта библиотека написана на C++ и имеет собственный движок инференса, ей не нужен PyTorch.
- **Для токенизатора:** `transformers.AutoTokenizer` использует Rust-библиотеку `tokenizers`. При импорте `transformers` он пытается подтянуть PyTorch, но это можно отключить, или использовать библиотеку `tokenizers` напрямую.
- **Для MLX-Audio:** Модели MLX загружают веса через `safetensors` или напрямую из форматов HuggingFace.
- **План действий:** Удалить `torch`, `torchaudio`, `accelerate` из зависимостей. Приложение будет запускаться в 3-4 раза быстрее и экономить сотни мегабайт ОЗУ.

## 3. Оптимизация локального перевода (CTranslate2)
**Текущая проблема:**
CTranslate2 инициализируется как `ctranslate2.Translator(model_path, device="cpu", compute_type="int8")`.

**Решение:**
- На чипе M1 CPU инференс работает отлично, однако можно явно ограничить количество потоков, чтобы не блокировать UI:
  `ctranslate2.Translator(..., inter_threads=1, intra_threads=4)` (4 потока — оптимально для 4-х производительных ядер M1).
- Убрать использование тяжелого `transformers.AutoTokenizer`. Вместо него можно использовать более легковесный `sentencepiece` (уже есть в зависимостях), если модель (например, `opus-mt`) основана на SentencePiece.

## 4. Управление памятью и выгрузка моделей (Garbage Collection)
**Текущая проблема:**
Модели Qwen3-TTS (MLX) и CTranslate2 загружаются в ОЗУ (в сумме около ~800 МБ - 1 ГБ) и висят там до закрытия приложения (из-за `self._model_lock`). На 8 ГБ M1, где ОС и браузер уже "съели" 6-7 ГБ, это приводит к своппингу (swap) на SSD при долгих паузах.

**Решение:**
- Внедрить **Auto-Unload (Таймер бездействия)**: Если пользователь не переводит ничего в течение 5 минут, явно удалять инстансы моделей (`self._model = None`, `self._ct2_translator = None`) и вызывать сборщик мусора (`import gc; gc.collect()`; для MLX также `mx.metal.clear_cache()`).
- При следующем запросе модель загрузится заново за 1-2 секунды, что является приемлемым компромиссом для сохранения ОЗУ свободной в фоновом режиме работы.

## 5. Заметки по локальным LLM (Ollama / LM Studio)
В `translator.py` дефолтными моделями прописаны `qwen2.5:7b`. На машине с 8 ГБ ОЗУ загрузка 7B модели в 4-bit квантовании займет около ~4.5 ГБ единой памяти. Это приведет к сильным тормозам всей системы.
**Рекомендация:**
Добавить в интерфейс настроек или README предупреждение для пользователей 8GB Mac: использовать либо CTranslate2 (лучший локальный выбор), либо облачный Gemini. Если принципиально нужен локальный LLM — рекомендовать модель `qwen2.5:1.5b` или `gemma2:2b`.
